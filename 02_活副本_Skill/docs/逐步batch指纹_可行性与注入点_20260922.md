# 逐步 batch 指纹：可行性与注入点（2026-09-22）

> **这份文件回答一个问题**：在**不改框架**的前提下，能不能客观回答"两次运行**每一步喂进去的 batch 是不是同一批数据**"？
> 此前它一直挂在我的"阻塞"栏里，理由是"`50_train.py` 没有数据通路钩子，管线在第三方 `mindspeed_mm` 里"。
> **那个理由是错的**：钩子是框架**官方提供**的。本文件记录查证过程、注入点、以及一个会让 A/B 静默失真的陷阱。
> **状态：设计完成，未实跑。** 先读 `trainer.py` 的 `__main__`（见 §5 待办），再写包装入口——**不猜接口**。

## 1. 为什么需要它（它补的是正确性链上唯一的空洞）

已有的证据链（见 `protocols/numeric_diag_phase1b_v2.json`）：

| 环节 | 结论 | 强度 |
|---|---|---|
| 启动输入 dump（19 行） | 四臂 `sha256=ec701fb9d5ebd668` **完全一致** | 强（逐字） |
| 第 1 步 loss | 在 `use_deter_comp=false` 下四臂相同 | 强 |
| 第 1 步 grad_norm | **不同**（47.326 / 47.34 / 47.337） | 弱（只有 3 位有效数字的输出） |
| 100 步权重 | `deter=false` 两轮 **320/473 张量不同**（max_abs 1e-4~1e-3，无非有限） | 中 |
| `deter=true` 正对照 | **473/473 逐位相同**（`CKPT_IDENTICAL`） | 强（正对照） |

⇒ **缺的那一环**：`deter=false` 下"两次运行从第几步开始分岔"，我们**只能从 loss/grad_norm 的打印去猜**，
因为"喂进去的数据"是否逐步相同**从未被直接观测**。log 里的 loss 是 4~6 位有效数字的舍入值，
分岔点落在打印精度之下就看不出来（坑 170 同族：**判据的分辨率低于现象的尺度**）。
逐步 batch 指纹把"数据侧是否相同"从"推断"变成"逐字可比"。

## 3. ★ 陷阱：注入 provider **本身就是换了一条数据流**

`get_dataloader()`（`trainer.py:339-400`）在构建之后**还做了后处理**，而 `dataloader_provider` 的返回值
**直接**被当作 `train_dataloader`（L79），**不经过那些后处理**：

| 后处理 | 条件 | 若被丢掉会怎样 |
|---|---|---|
| `train_dataloader = PrefetchGradAccDataLoader(train_dataloader, grad_acc_step=args.training.gradient_accumulation_steps)` | **仅当** `args.features.loss_cfg.loss_type == "per_token_loss"` | 梯度累积的预取/切分语义改变 ⇒ 与基线**不是同一条数据流**，A/B 不可比 |
| 训练集/验证集拆分（`build_mm_dataset` 返回 tuple 时取 `[0]/[1]`） | 总是 | 数据集取错（把 val 当 train） |
| `val_dataloader` 的 `shuffle=False / drop_last=False / val_micro_batch_size` 覆盖 | `val_interval > 0` | 验证语义与本轮无关，但**说明 provider 必须自己交代这些** |

**因此定纪律**：
- 用 provider 的诊断运行 **必须**声明 `plan_consistent = false`（它本来就与基线不同一条数据流）；
- provider 里**必须逐行复刻** `get_dataloader()` 的行为（含上面三条），并**在日志里打印一行自证**
  （例如 `FP_PROVIDER_MIRRORS get_dataloader=True loss_type=per_token_loss prefetch_wrapped=True`），
  否则"我只是加了个 logger"这句话**没有依据**；
- 更稳的替代（若只想取证、不想碰数据流）：让 provider **先调用默认构建**，再**只在最外层套一个只读代理**——
  仍属"换数据流"，仍按上面声明，但至少内层与默认路径**同一份代码**。

## 3bis. ★ 更好的做法（**首选**）：子类覆写 `get_dataloader`，不用 provider

读完 `trainer.py` 后发现的方案，**比 provider 更稳**，因为它把 §3 的陷阱从根上绕开了：

```python
from mindspeed_mm.fsdp.train.trainer import Trainer

class _FPTrainer(Trainer):
    """只覆写 get_dataloader：默认数据流的代码**一行不改**，只在最外层套一个只读代理。"""
    def get_dataloader(self):
        res = super().get_dataloader()          # ← 框架原封不动的构建（含 PrefetchGradAccDataLoader、
                                                #    train/val 拆分、val 的 shuffle/drop_last 覆盖）
        train_loader = res[0] if isinstance(res, tuple) else res
        wrapped = _batchfp.wrap(train_loader)   # ← 只读代理：转发一切，仅在 __iter__ 时记指纹
        return (wrapped, res[1]) if isinstance(res, tuple) else wrapped

...
_FPTrainer(args=arguments).train()
```

为什么它优于 provider：

| 维度 | provider（§2/§4 原方案） | **子类覆写（首选）** |
|---|---|---|
| 默认构建代码 | 需**逐行复刻** `get_dataloader()`（100+ 行，任一处漏掉就静默失真） | `super()` 调用**同一份代码**，无复刻 |
| `PrefetchGradAccDataLoader` 条件包装 | 必须自己判断 `loss_type == "per_token_loss"` | 自动继承 |
| train/val 拆分、val 参数覆盖 | 必须自己处理 | 自动继承 |
| 失效模式 | **漏复刻 ⇒ 静默换数据流**（最难发现） | 只有"代理写错"一种，且代理是转发器，易测 |
| `plan_consistent` | `false`（且需自证复刻正确） | 仍应声明 `false`（对象毕竟不同），但**数据流语义由构造保证** |

⇒ **实现顺序**：先做子类覆写；provider 只在"必须替换掉框架构建"时才用，且那时 §3 的全部纪律生效。

2. `scripts/_batchfp.py`：**只读代理**（首选路径用它；provider 只在必须替换框架构建时才用），逐微批打印
   `BATCHFP step=<k> micro=<m> keys=<排序键名> shapes=<…> sha256=<张量字节摘要>`（**每步一行**，rank0）。
3. 判据（**先冻结后执行**，写进新的 protocol JSON）：
   - 同配置两次运行 ⇒ 若 `BATCHFP` 逐行相同而权重仍不同 ⇒ **分岔不在数据侧**（把嫌疑收敛到算子/并行/通信）；
   - 若第 k 步 `BATCHFP` 不同 ⇒ **首个不同步就是数据侧**（比从 4 位小数 loss 猜要强得多）。
4. **负向对照（必须做，否则"相同"没有含义）**：故意改一个 batch 相关量（如 `seed` 或 `cutoff_len`）
   跑一轮，`BATCHFP` **必须**出现不同行——这条是本判据的"够灵敏"证明（坑 187 的教训：正/负对照都是判据的一部分）。

## 5. 边界（这份设计**不能**证明什么）

- ❌ 不能证明"框架内部没有不确定性"：指纹只覆盖**进入模型前**的张量，模型内部（算子归约顺序、通信）不在其中。
- ❌ 不能替代 `deter=true` 正对照：那条证明的是"确定性路径下可逐位相同"，与本指纹互补。
- ❌ 用 provider 的那次运行 **不是** 基线的可比值（见 §3），不得与基线做性能/收敛对比。
