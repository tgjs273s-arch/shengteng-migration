## 探测结果如何读

`python scripts/05_preflight.py --json --want quick|full` 写 `out/preflight/capability.json`。`rows` 中每项有 `capability/status/evidence/impact`；`profile` 还保存 `python_exe`、NPU、`torch_npu`、CANN/driver、网络及本次新增的 `torch_torch_npu_pair`、`mindspeed_mm_source`。`mindspeed_mm_source` 的 `entry_present` 只表示存在 `mindspeed_mm/fsdp/train/trainer.py`，`git_commit` 是**该目录自身 checkout** 的 HEAD，`git_dirty` 表示本地改动；三者都不证明与尚未取得的指定目标 commit 一致。缺训练入口为 BLOCKED；有入口但源码身份或目标配对未确认时为 DEGRADED。`torch_torch_npu_pair` 只比较两包的前三段版本数字：相同标 OK，失配标 DEGRADED，未知标 SKIP。这只是诊断信息，不构成硬性配对闸门；实际约束须来自冻结的目标依赖及实测，不能由数字相同推断 CANN、Triton、框架 API 或训练可用。`triton_ascend_kernel=OK` 需本次最小 NPU kernel 返回码和成功标记，包可导入不等于 kernel 成功；替代后端数值等价仍待验证。

`00_probe_env.py` 的 `out/probe/env.json` 另保存 P0 硬件、软件、前置条件、资源与推荐档位。它仍以裸 `python3` 启动若干子探测；这可能与 PRE 的 `python_exe` 及 `bringup.sh` 的 `PYBIN` 不同。解释器不一致时不能合并两份环境快照为同一运行环境。T02 未扩展修改 P0 的整套 shell 探测；目标机器上应分别记录 `command -v python3`、`sys.executable`、`PYBIN` 和安装位置，再决定是否统一调用链。

## 副作用与安全边界

- `_envcompat.py --json` 读取本机环境；`05_preflight.py` 会执行只读硬件/网络检查，并可能运行实际 Triton NPU kernel，写降级记录；`--json` 另写公共 `out/preflight/capability.json`。公共 `out/` 不支持并发。
- `00_probe_env.py --quick` 跳过耗时 kernel，正常模式可能启动该 kernel，写 `out/probe/env.json`。`--selftest` 只测档位规则，不是当前硬件验证。
- `bringup.sh` **不是探测命令**。它会安装系统包与 pip 包、克隆外部源码、准备/转换资产，并在 phase4 运行 mock 训练；部分路径写在 `/root`，phase2 还会尝试移走旧 MindSpeed checkout。运行前需核对真实机器、隔离环境、入口版本、权限、磁盘与任务授权。旧 `versions.lock` 的安装行不是当前机器处置方案。
- P4 可下载大文件并转换权重；`run_from_zero.sh --quick` 仍可能进入训练。缺资产或无 NPU 时只记录受阻，不以合成样本、包导入或旧日志代替本次验证。

本地只读核对可分别查看 `python --version`、`python -m pip --version`、`python scripts/_envcompat.py --json` 与 Git checkout；这些结果必须附解释器路径和时间。目标实机快照至少需 OS/架构、设备与驱动、CANN 路径及版本、Python 可执行文件、包版本、MindSpeed/MM commit 与工作树状态、Triton backend/kernel 结果，以及本次模型/数据身份。当前 Windows 主机没有本轮 NPU 实测快照，不能将历史 A3 或 machineB 数字写为本次结果。
