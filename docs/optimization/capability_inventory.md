## 按优先级排列的问题

### F01 P0 主入口可将失败阶段误判为通过

位置：`02_活副本_Skill/scripts/run_from_zero.sh:118`、`:195`、`:262`。

run_stage 捕获退出码后主要按独立产物判据决策；P2 只检查配置文件非空，P5 只检查训练日志出现 iteration。若本轮配置生成失败但旧配置仍在，或训练中途失败但已经打印 iteration，外层仍可 PASS，弱于 50_train.py 本身的失败判据。主入口也未根据上游状态阻断依赖它的下游。

建议：区分诊断继续与业务依赖阻断，显式检查退出码和结果状态，按运行 ID 隔离产物。验证：注入失败返回码并保留旧产物，下游应 BLOCKED，独立诊断仍可运行。

### F02 P0 P1 到 P2 的迁移点字段不一致

位置：`10_analyze_points.py:139` 与 `20_plan_migration.py:408`（均位于 02/scripts）。

P1 输出 points，P2 读取 categories 或 summary，正常产物在映射表中得到空字典。训练配置仍可生成，但“识别结果进入迁移方案”的链路缺失。

建议：统一输入契约并校验结构，兼容旧格式时显式声明。验证：含四类 points 的输入应产生对应映射行，非法输入不静默转换成空结果。

### F03 P0 算子失败未影响阶段成功状态

位置：`30_verify_ops.py:37`、`:109` 和 `run_from_zero.sh:225`。

run_matrix 将异常记录为 error 后继续；main 无条件打印三类 forward 贯通，正常退出并写 JSON。主入口检查文件及少量日志关键词，不检查 matrix 中的 error。因此错误可被当作阶段通过。GatedDeltaNet 的 contract-only 是明确能力边界，不应强行改成成功。

建议：按实际行状态生成汇总与退出码，区分失败、部分验证和仅契约。验证：模拟一个算子抛异常，必须反映在汇总与外层阶段状态中。

### F04 P0 工具链仍依赖原作者目录

位置：`03_工具链/prepush_check.py:38`、`:44`、`:342`，`safe_pack_sync.py:42`，`check_report_pdf.py:31`。

无法用当前工作区的检查结果代表本项目；当前不执行这些硬编码入口。另确认 prepush 的 G22 当前使用 --verify-only，不能根据顶部旧注释认定它仍传 --apply。

建议：统一根目录参数或相对位置推导，再验证实际检查范围。`safe_pack_sync.py:229`、`:248` 存在 shutil.rmtree；按用户禁止批量删除的要求，不执行该 apply 路径，后续另行改造。
