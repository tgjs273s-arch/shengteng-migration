> C4-AI 2026 昇腾赛道复赛 · Qwen3.5-0.8B 训练迁移（MindSpeed-MM / 昇腾 910C）
> 交付物类型：性能测试报告（官方模板格式）

> 生成日期：2026-09-11（性能实验执行日：2026-09-10；对照官方基线：2026-07-24）

## 核心结论

> **单步耗时 21,393 ms → 419.0 ms（51.1×）；50–100 步性能优于官方基线
> （中位 419.0 ms vs 官方 431.3 ms；均值 430.1 ms vs 官方 649.3 ms）。**

| 指标（50–100 步，GBS=8） | 官方 7/24 基线 | **本队（910C 双 die）** | 对比 |
|---|---|---|---|
| 平均每迭代耗时（**中位**） | 431.3 ms | **419.0 ms** | **快 2.8%** |
| 平均每迭代耗时（均值） | 649.3 ms | **430.1 ms** | **快 1.51×** |
| **每秒样本数**（中位口径） | 18.55 | **19.09** | **+2.9%** |
| **每秒样本数**（均值口径） | 12.32 | **18.60** | **+51.0%** |
| 相对迁移前（eager 实现） | — | **21,393 → 419.0 ms** | **51.1×** |

> 每秒样本数 = GBS × 1000 / STEP_TIME（GBS=8），与官方脚本口径一致。

> ⚠ **必读**：上述 419.0 ms 是 **2026-09-10 那台宿主**上的实测值。2026-09-16/17 的重复实验发现
> **同一份代码、同一几何、同一窗口在不同"容器运行时段"上可以差 2.27×**
> （最慢 946.4 ms ↔ 最快 417.1 ms；2026-09-16 批次 925.4 ms）。
> 该现象与其判据见文末「附：性能的节点依赖性」——**引用本报告任何性能数字时必须同时说明所在时段/节点身份**。

## 技术思路：先测准瓶颈，再找结构杠杆（而非盲目调参）

1. **用 profiling 定位瓶颈类型**——实测每步约 1.4 万个 kernel 发射，计算仅占 stage 时间 23%，
   即**瓶颈是 kernel 发射次数（launch-bound）而非算力**。由此得到关键杠杆：
   **kernel 数正比于 micro-batch 个数**。
2. **"每级只改一个变量"的八级优化**（见下表汇总），每级收益均可在对应日志复核：
   算子实现（3.44×）→ 几何/micro 数（2.04×）→ 硬件换代（1.80×）→ 几何细化（1.71×、1.32×、1.37×）
   → 关闭过期显存开关（1.22×）→ FSDP 参数预收集（1.08%，并消除长尾慢步）。
3. **三个反直觉发现**（均出自实测，非推测）：
   - 配置中为 32GB 显存环境设的 `recompute / chunk_loss / activation_offload`，在 128GB 卡上**纯属开销**
     → 关闭后单步 549.8 → 451.0 ms，且 **step1 loss 逐位不变**（证明只影响"显存↔时间"取舍）。
   - FSDP `prefetch` 深度**加深反而变慢**（2/2 比 1/1 慢约 40 ms）；而 `pregather=true` 消除了
     周期性 3.7 s 慢步（100 步中由 8 个降至 1 个）。
   - `TASK_QUEUE_ENABLE=1` 或 `pin_memory=false` 会使慢步回归 → 该两项不可动。
4. **性能与精度同时成立**——所有优化均在**不改变数值路径**的前提下完成，最终 step1 loss
   仍与官方逐位一致（1.924621）。

## 优化点 1：GDN 算子 NPU Triton 实现

**优化点说明**

Qwen3.5-0.8B 的 GatedDeltaNet（GDN）在昇腾生态无现成实现。初始以 eager（逐算子拼接）运行，
单步 21393 ms。将其 `causal_conv1d` 与 `chunk_gated_delta_rule` 前反向全部切换为 **NPU Triton**
实现（`gdn_implementation: triton`、`causal_conv1d_implementation: triton`），单步降至 **6213 ms**。

关键工程点：昇腾 910C（设备名 `Ascend910_9382`）需要 **triton-ascend 3.2.2**（CANN 9.1.0 +
torch 2.7.1 + py3.10 的官方配对版本），且需 `python3-dev + build-essential` 以支持驱动的
C++ 桥接现场编译。日志证据：`use NPU triton ops` 命中 36 行，`roll back to CPU` 命中 **0** 行
（由 SK04 `fingerprint_observed` 机器提取）。

**性能收益：21393 → 6213 ms（3.44×）**；每秒样本数 0.37 → 1.29。

## 优化点 2：几何优化（减少 micro-batch 个数）

**优化点说明**

profiling 显示训练为 **launch-bound**：每步约 1.4 万个 kernel 发射，计算仅占 stage 时间的 23%，
其余为发射间隙与同步。而 **kernel 数量正比于 micro-batch 个数**（每 micro 一次完整前反向）。
在 GBS=8 约束下，将 `micro_batch_size` 由 1 提升到 2、`gradient_accumulation_steps` 由 8 降到 4，
micro 个数由 8 降到 4。单步 6213 → **3051 ms**。

**性能收益：6213 → 3051 ms（2.04×）**；每秒样本数 1.29 → 2.62。

---

## 优化点 3：迁移至昇腾 910C

**优化点说明**

在完全相同配置（m2g4/triton/GBS=8）下由 910B4 迁移到 910C 双 die 卡，单步 3051 → **1696 ms**。
跨卡数值等价性已单独验证：910B4 vs 910C 逐步 loss 偏差最大 0.196%、均值 0.059%，
grad_norm 偏差最大 0.60%，满足数值等价前提。

**性能收益：3051 → 1696 ms（1.80×）**；每秒样本数 2.62 → 4.72。

---

## 优化点 4：几何优化（m4g2，64GB 显存解锁）

**优化点说明**

910B4（32GB）上 m4g2 几何必然 OOM（iter9 时占用 29.5GB）；910C 单 die 64GB 解除了该限制，
m4g2（micro 个数 2）顺利完成 100 步，单步 1696 → **992 ms**，显存 reserved 26.4GB/64GB。

**性能收益：1696 → 992 ms（1.71×）**；每秒样本数 4.72 → 8.06。

---

## 优化点 5：几何优化（m8g1，单 micro 上界）

**优化点说明**

GBS=8 约束下单 die 的几何上界为 `mbs=8, gas=1`（micro 个数 = 1）。m8g1 单步 **752 ms**，
reserved 34.2GB/64GB，无 OOM。此为单 die 的极限几何。

**性能收益：992 → 752 ms（1.32×）**；每秒样本数 8.06 → 10.64。

---

## 优化点 6：复刻官方并行几何（双 die dp2）

**优化点说明**

经 `npu-smi` 实测确认：本机算力为 **1 张 910C 双 die 卡**（单卡 2 芯片、合计 128GB），
与官方 7/24 基线日志的运行拓扑（`NPUS_PER_NODE=2`）一致——此前仅使用其中 1 个 die。
改用官方几何 `world_size=2 / mbs=4 / gas=1 / dp=2` 后，单步 752 → **549.8 ms**。

该优化同时解决**精度可比性**：mbs/gas/dp 三维配置指纹归零、每步 batch 组成与官方物理一致。

**性能收益：752 → 549.8 ms（1.37×）**；每秒样本数 10.64 → 14.55。

---

## 优化点 7：关闭过期的显存节省开关

**优化点说明**

配置中保留着为 32GB 显存环境（910B4）设置的三个显存节省选项，但在 128GB 的 910C 上
（实际激活占用仅约 230MB）它们**只产生开销、不带来收益**：

| 开关 | 原值 | 作用（在 64GB/die 下的实际效果） |
|---|---|---|
| `features.recompute` | true → **false** | 原为省激活显存而重算前向，纯增开销 |
| `features.enable_chunk_loss` | true → **false** | 原为分块计算 loss 省显存 |
| `features.enable_activation_offload` | true → **false** | 原为把激活搬到 CPU 省显存，引入搬运开销 |

三项关闭后单步 549.8 → **451.0 ms**，且**第 1 步 loss 逐位不变（1.924620）**——
证明这些开关仅影响"显存↔时间"取舍，不改变数值路径。

**性能收益：549.8 → 451.0 ms（1.22×）**；每秒样本数 14.55 → 17.74。

---

## 优化点 8：FSDP 参数预收集（pregather）

**优化点说明**

通过对 5 个变体做单变量分离实验（各 20 步，同一数据同一顺序），定位到两类问题并解决：

| 变体 | 快步中位 | 慢步数（>1s） | 结论 |
|---|---|---|---|
| 基准（无 pregather, prefetch 1/1） | 457 ms | 8 | 存在 3.7s 级加载阻塞慢步 |
| prefetch 2/2 + pregather | 496 ms | 1 | prefetch 加深有害（-40ms） |
| prefetch 2/2，无 pregather | 509 ms | 1 | 缺 pregather 时快步退化 |
| **prefetch 1/1 + pregather=true** | **452 ms** | **1** | ✅ 最优 |
| TASK_QUEUE=1 + pin_memory=false | 477 ms | 6 | 该两项不可动 |

结论：**开启 `fsdp_plan.pregather`（参数预收集）可消除 3.7s 级周期性加载慢步**，
同时保持 prefetch 深度为 1/1（加深反而变慢）。100 步实测：50–100 中位 **419.0 ms**，
全程仅剩 1 个慢步（iter1 首次编译 6.7s），此前配置有 8 个 3.7s 慢步。

**性能收益：451.0 → 419.0 ms（1.08×）**；每秒样本数 17.74 → 19.09。

## 附：性能的节点依赖性（2026-09-17 新增，必读）

### 结论

**同一份 Skill 源码、同一官方几何（GBS=8、dp=2/mbs=4/gas=1）、同一官方窗口（50–100 步），
在不同"容器运行时段（epoch）"上的窗口中位可以相差 2.27×**：
最慢时段 **946.4 ms**（2026-09-17 时段 A），最快时段 **417.1 ms**（2026-09-17 时段 B）。
**两个时段是同一天、同一台目标机地址，但容器 boot_id 不同**（容器被重新调度）。
⇒ 本项目的性能数字**依赖所在宿主会话**；419.0 ms 与官方 431.3 ms 的可比性成立，但**必须绑定节点身份**。

### 时段对照（每个记录自带 `identity.boot`，可自证来源）

| 时段 | `identity.boot` | 窗口 50–100 中位 | 说明 |
|---|---|---|---|
| 2026-09-10（**交付主口径**） | 未记录 | **419.0 ms** | A3 最终验收 100 步 |
| 2026-09-16 | 未记录（hostname `3fc7234f6f87`） | **925.4 ms**（均值 983.3，最快步 775.1） | 包内 `train.log` 即此批 |
| 2026-09-17 时段 A | `8d1d0a74-ff61-48fa-be62-f987e0c59a2a` | **946.4 ms** | T3 首批（2 组中 1 组通过成败判据） |
| 2026-09-17 时段 B | `7bcced6f-26df-4169-ae9c-eea0227981dd` | **417.1 / 423.4 / 426.0 / 433.0 / 445.0 / 451.7 ms**（6 组） | T3 r2：default 组均值 **436.900**（sd 13.286）、OMP=32 组均值 428.500（sd 14.632） |

另有一项**不同窗口**的旁证（窗口 11–30，九组线程矩阵，2026-09-16/17 时段）：**895.20–928.80 ms**，
极差仅 3.75%。

### 判据（为什么可以下"时段差异"这个结论）

1. **源码同源**：时段 B 的 6 组 `source_sha256` 完全一致 → 不是改代码改快的；
2. **几何同源**：运行时日志 `global batch size: 8` + dp2/mbs4/gas1 → 不是换几何；
3. **口径同源**：`steps_used=51`、窗口 50–100 → 不是换窗口；
4. **身份自证**：时段 B 内部 6 组 `identity.boot` **完全相同**，而时段 A / 时段 B **boot_id 不同**
   → 变量是"容器被重新调度到的宿主会话"，不是日期、不是负载时段；
5. ⇒ 三项同源 + 身份自证的条件下，唯一系统性变化是**运行所在时段（宿主会话）**。

### 这个差距**不是**线程配置造成的（九组线程矩阵）

九种 `OMP ∈ {default,8,32} × workers ∈ {8,16,24}` 组合（每组 30 步、dp2/mbs4/gas1、串行）：
窗口 11–30 中位 **895.20–928.80 ms**，极差仅 3.75%，OMP=32 组合与 default 组合**交错重叠** ——
在慢时段里，**任何线程配置都拉不回来**。

### 机制（诚实边界）

在 2026-09-17 时段 B 上训练期同步采 `npu-smi -t usages`：**AICore 从 16% 能冲到 95%、HBM 带宽 15–48%**；
慢时段同期为 AICore 49–64%、HBM 4–6%。这与"慢时段把 NPU 喂不饱（宿主侧供给不足）"一致。

> **但本节只是机制"支持"，不是"定论"**：采样间隔 4 s、步长 ~0.43 s，存在混叠，
> 瞬时值在 16↔95 间摆动，**不能当稳态利用率**；若要正式主张需 ≤0.5 s 采样或 `msprof` 时间线。
> 本项目纪律：**未分离的机制不单独归因**（不得把邻居负载 / NPU 频率 / 机型拓扑任一条单独断言为原因）。

### 适用条件（引用本报告数字时请一并给出）

1. 报告中的 419.0 ms（含全部优化点 1–8）来自 **2026-09-10 的宿主时段**，不是"任意节点都能复现"；
2. 性能证据**必须附当次运行节点的 `boot_id` / `hostname`**（接手方的 `identity` 字段即为该实践）；

### 附：剩余性能余量的量化（诊断，**上界而非承诺**）

为了回答"还能快多少"，在**同一快时段**上做了**三点分离 + 预登记第 4 点**实验（30 步/点，串行）：

| 点 | 几何 | 窗口 11–30 中位 |
|---|---|---|
| A | mbs4 gas1 **GBS=8（官方几何）** | **432.7 ms** |
| B | mbs8 gas1 GBS=16 | 715.5 ms |
| C | mbs4 gas2 GBS=16 | **862.4 ms**（与 B 同批量，仅拆成 2 个 micro-batch → **慢 20.5%**） |
| D | mbs8 gas2 GBS=32 | **1354.3 ms**（事前预测 1428.0 ms、容差 ±10% → **命中**，把"三点必然拟合"变成可证伪检验） |

解出：每样本计算 **70.7 ms/样本**、**每 micro-batch 固定开销 146.9 ms**、每步固定 3.0 ms。
⇒ 官方几何每步 **432.7 ms = 146.9（34%，与样本数无关的固定开销）+ 282.8（65%，算）+ 3.0**。

独立复核（profiler 五桶，`step_trace_time.csv`，同几何、同一时段）：

| 桶 | ms | 占 Stage |
|---|---|---|
| Stage | 458.93 | 100% |
| Computing | 312.52 | 68.1% |
| **Communication（未重叠）** | **40.32** | 8.8% |
| **Free** | **106.04** | 23.1% |

**两条独立路径吻合**：`Free + 未重叠通信 = 146.36 ms` vs 三点拟合的 `146.9 ms`（差 **0.4%**）。
发射密度 **≈6,994 次 kernel/步**（106 ms ÷ 6,994 ≈ 15 µs/次）。

> **因此："若固定开销能消除，理论下限 286.3 ms → 相对官方 431.3 ms 是 1.51×"。**
> 这是**上界，不是承诺**：① 它假设 Free 与未重叠通信可全部消除；② 归因到"下发 / 数据等待 / 同步点"
> 三者中的哪一个**尚未分离**（下一步实验已定判据）；③ profiler 运行会拖慢训练，其绝对时长**不用于对标**；
> ④ 结论绑定该时段 `identity.boot`。方法篇见 Skill 内 `docs/性能余量量化.md`。

**固定开销的归因（已完成）**：用 `kernel_details.csv`（**6,994 次发射/步**）重建设备时间线 +
`api_statistic.csv`（宿主侧 API）交叉验证 → **下发为主（launch-bound）**：

| 证据 | 数值 | 读法 |
|---|---|---|
| 相邻 kernel 空隙 | **3,398 个/步**，总时长 **144.65 ms/步**（≈固定开销的 98.8%） | 设备频繁等下一发 |
| 其中 ≤50 µs 小空隙 | **占个数 87.4%** | 典型**下发间隙** |
| 宿主侧 `launch` 族 | **62.9–100.6 ms/步** vs `Free` 106.0 ms（**0.59–0.95×**） | 与 Free 同量级 |
| >1 ms 大空隙 | 59 个 ≈ **54.7 ms/步** | 形态集中在 grad-norm/clip 往返与 `TensorMove→Cast`（同步/等待，**未单独证明**） |

⇒ **优化方向：减少发射次数 / 图执行**（小算子重灾区：`Transpose` **831 次/步**、`aclnnInplaceCopy` **≈2,188 次/步**）。
**注意**：`Free`/空隙时长**不等于可省时间**；且"关掉每步 loss/grad-norm 打印"属**负载变更**，不计为纯优化收益。
