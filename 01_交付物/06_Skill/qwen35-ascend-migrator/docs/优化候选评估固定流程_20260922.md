# 优化候选评估固定流程（产品化）—— 2026-09-22

> **这份文档回答一个问题：拿到一个"看起来能变快"的改动，本项目**按什么固定顺序**去评估它，
> 以及在什么条件下**才允许把它的数字写进结论**。**
>
> 起因（交接 §4-4）：本项目的性能纪律早就定死了，但**步骤散落在多个文档与几次会话里**，
> 全靠人记。本轮把它固化成一条**有闸门、有退出码、能 fail-closed** 的流程：
> `scripts/62_reportability.py` 是这条流程的**唯一硬闸门**（缺"先量噪声"这一步就拒绝出结论）。

---

## 0. 一句话流程

```
① 探测  →  ② 候选试跑  →  ③ 先量噪声(闸门)  →  ④ 正确性/资源检查  →  ⑤ 选档  →  ⑥ 输出证据与边界
                                ↑
                    ★ 62_reportability.py 在这里拦人：
                      没有同批次底噪 ⇒ 直接 INVALID，不许出数字
```

**顺序不可调换。** 尤其 **③ 必须在 ①②之后、④⑤之前**：先用同一批数据量出"这把尺子能分辨多少"，
再拿这把尺子去量候选。反过来做（先看候选快了多少，再去补噪声）会让"噪声"变成事后解释。

## 1. 逐步说明

### ① 探测（决定整条路径能不能跑）
- **动作**：`scripts/00_probe_env.py` → `out/probe/env.json`。
- **必须落盘的身份字段**：`hostname` + `npu-smi 版本` + `CANN 版本` + `boot id`。
- **判据**：路径档位（`full_npu` / `single_die` / `np0_triton_off` / `cpu_only`）必须被显式判定。
- **为什么要它**：**跨机/跨批次的绝对时间一律作废**（坑 209：同 IP 变更、同磁盘不同机，
  同一配置中位步时长 419.03 ms → 731.6 ms，相差 1.75×）。相对比较**只在同一批次内**成立。
- **不通过**：身份字段缺失 ⇒ 该轮所有绝对时间**不得**进入结论。

### ② 候选试跑（先把"能不能跑"和"跑得对不对"分开）
- **动作**：用 `50_train.py` 的正式计时入口跑候选，`--dry-run` 可先打印真实命令。
- **判据**：**先过"这一次运行有效"**（退出码 + 步号齐全），再看时间。
  `59`/`63` 的 `compute_valid()` 是**同一份**校验器（纪律 #8：同一语义只留一处实现）。
- **不通过**：无效运行**立刻停止**，不得把它算进中位数（否则等于给噪声加分）。

### ③ 先量噪声 ★**本流程的硬闸门**
- **动作**：**同批次、同配置重复 N 次**，不改任何键：
  ```bash
  python3 scripts/59_config_ab.py --null-test 3 --steps 100 --out out/ab_null
  ```
  产出 `out/ab_null/null_summary.json`（`schema=p59null.v1`，关键字段 `spread_pct`）。
- **本项目实测底噪**：`protocols/prefetch_depth_20260922.json` 的 `evidence.noise_floor` ——
  同机同会话两轮基线中位数 **731.6 ms / 716.5 ms ⇒ 漂移 ≈ 2.11%**。
- **闸门（`62_reportability.py`）**：
  ```bash
  python3 scripts/62_reportability.py --noise out/ab_null/null_summary.json \
      --ab out/ab/summary.json --out out/ab/reportability.json
  ```
  **阈值 = `max(2 × 实测底噪, 5%)`**，两个因子都有出处：
  | 因子 | 值 | 出处 |
  |---|---|---|
  | 底噪倍数 | **×2** | `protocols/prefetch_depth_20260922.json` → `rule_added`：「任何小于**噪声底噪 2 倍**的效应，一律先按 UNCERTAIN 处理」 |
  | 效应下限 | **5%** | 性能纪律：「实测底噪 ≈2%，**<5% 不可报告**」 |
  ⇒ 本设置下阈值 = `max(2×2.11, 5) = **5.0%**`（由 5% 下限决定）。
- **fail-closed（判不动就**不许**当通过）**：缺文件 / `runs<2` / `spread` 缺失或非有限 /
  `spread=0` / schema 不认识 / 效应 NaN·inf / 缺配对数 ⇒ **`INVALID_INPUT`（退出码 5）**。
- **不通过**：拿不到底噪 ⇒ **不许**出任何性能数字，只能做"跑通了/没跑通"的定性陈述。

### ④ 正确性 / 资源检查（性能结论**不得**替精度背书）
- **正确性**：`70_judge.py` 五态裁决（`POINTWISE_OK` / `WINDOW_OK` / `NEEDS_EVIDENCE` /
  `NOT_COMPARABLE` / `INVALID_INPUT`）；逐点比对前**先**用零假设实验证明"同配置重复跑 loss 逐点相同"，
  否则逐点判据在这条数据路径上**不可用**（坑 155：`REJECT_NUMERIC` 会被错误归因给被测键）。
- **资源**：`56_profile_run.py`（桶/算子/栈/显存）确认改动没有把成本挪到别处
  （本项目实测：`wait_event` ≈46.6%、其中 `reduce_scatter` 17.45%、重算仅 0.78%）。
- **判据**：正确性未闭合 ⇒ 该候选**不得**进入推荐配置（"快"没有意义，如果它算错了）。

### ⑤ 选档（把候选分成三等，而不是二值）
| 档 | 条件 | 处置 |
|---|---|---|
| **采用** | `performance_pass=true`（**区间下界 ≥ 阈值**）且 `run_validity=OK` 且 `accuracy_validity=OK`（⇒ `adoption_ready=true`） | 写入推荐配置，数字进结论 |
| **同向但不报告** | 效应方向为正但 **95% 区间下界 `< 阈值`**（`CI_LOWER_BELOW_THRESHOLD`） | 记为「已排查、证据不足以支撑 ≥5%」——**这本身是有价值的信息**，但不给数字 |
| **排除** | ① `PERFORMANCE_NOT_MET`（区间下界 < 阈值，**不是**"点估计没过 5%"）；② 正确性/资源倒退；③ 方向不一致 / 复现失败 | 写明排除理由与批次 |

★ 另有一档中间态：**`PERFORMANCE_MET_ADOPTION_BLOCKED`（退出码 3）** ——
性能达标，但运行/精度关未闭合 ⇒ **性能结论成立、但不可采纳**。

★ **"方向为正但不过阈值"与"没效应"必须分开写**：前者是"这把尺子在这个量级上分不出来"，
后者是"真的没有"。`62` v2 的 `reason` 字段正是为了这个区分（`CI_LOWER_BELOW_THRESHOLD` vs `PAIRS_LT_MIN`）。

### ⑥ 输出证据与边界
- 产物：`out/reportability.json`（v2 字段：`verdict` / `reason` / `threshold_pct` /
  `savings_pct` / **`ci95_savings_pct`** / `run_validity` / `accuracy_validity` /
  `performance_pass` / `adoption_ready` / `baseline_run_id` / `candidate_run_id` /
  `denominator` / `roles_assumed` / **`claim_scope`**）。
- **`claim_scope` 必须与数字同现**（自动写入，防止下游漏抄限定语）：
  - `official_comparable=false`（mock 数据）⇒ `同机同批次（非官方可比）：不得声称优于官方基线`
  - `official_comparable=true` ⇒ 换官方可比几何的限定语
- **铁律**：`official_comparable=false` 时，**只**能说"同机同批次的相对差"，**不得**给出与官方的比值。

## 3. ★ 角色与分母：不再依赖 A/B 字母

**`variant` 的 A/B 指的是"两个配置"，不等于"基线/候选"。** 本项目就踩了这个坑：
要评估「配置 A（推荐）相对 配置 B（保底）省时」，**候选是 A、基线是 B**
⇒ 必须 `--baseline-variant B --candidate-variant A`。
默认按 A/B 假定角色时，产物里标 `roles_assumed=true` 并打印告警（**假定不得当声明**）。

**统一口径（写进产物）**：

```
savings_pct = (baseline − candidate) / 分母 × 100        ★ 正号恒等于「候选更快」
分母 = --denominator {baseline, candidate}（默认 baseline = 标准省时比例）
ci95_savings_pct = 同一口径下的 95% 区间（逐对比值 → 配对 t 区间）
```

两条**必须**同时遵守：
1. **逐对比值再取均值**（配对设计），**不能**用"均值的比值"代替 —— 后者给 **19.608%**，
   与主口径差 0.002pt（`62` 自检里有一条专门盯这个差别）。
2. 旧版的 `savings_b = (B−A)/B` 里**正号表示 B(候选)更慢**，与正文"省时"的正号**相反**
   ⇒ 曾出现"点估计写正、区间写负"的自相矛盾。v2 用**角色制 + 单一方向**消除该歧义。

**已复现验证**（`62 --selftest`，30 例全过，含 2 例**真的起子进程**的端到端断言）：
用 `AB_AVSB_20260921__summary.json` 的三对真实窗口中位数
（配置 A=418.600/418.000/420.500 ms，配置 B=521.450/522.850/519.400 ms）
⇒ `62` 复算出 **savings_pct = 19.6062%**、**95% 区间 [18.3235, 20.8889]**，与交付文档**逐位一致**。

## 5. ★ 首次实战：§4-2 代码级候选（本流程的第一次完整应用）

**候选**（交接 §4-2）：`clip_grad=0.0` 时仍每步调用 `clip_grad_norm`；`average_losses_across_data_parallel_group` 每步 `all_reduce`。

**结果：两个候选都被排除，且理由是「代价 > 收益」，不是「没到 5%」。**

| 步骤 | 做了什么 | 结论 |
|---|---|---|
| ① 探测 | 实读远端源码定位调用点（`clip_grad` @ `train_engine.py:263`、loss @ `:183`），核实 `max_norm=0` 语义 = 「只算范数不裁剪」 | 候选真实存在 |
| ② 候选试跑 | 先做**归因**（见下），据此判断值不值得跑端到端 | 归因上界 < 5% |
| ③ 先量噪声 | **做了**：同批次 N 臂 3 轮 ⇒ 底噪 **1.53%**；再跑 3 臂 × 3 轮 A/B（拉丁方平衡顺序） | 阈值 = `max(2×1.53, 5) = 5.0%` |
| ④ 正确性/资源检查 | `--with-stack` profile + `kernel_details.csv` 算子归因；并清点**观测代价** | 见下两节 |
| ⑤ 选档 | **排除**（第 3 档，`PERFORMANCE_NOT_MET / CI_LOWER_BELOW_THRESHOLD`） | — |
| ⑥ 输出边界 | 落盘 `protocols/codelevel_sync_candidates_20260922.json` + **更正文件 `…_CORRECTION_v2_20260922.json`** | — |

★ **关于 ③ 的判据扩展（如实记录）**：协议原先写的是「归因上界 < 5% ⇒ 不触发 A/B」，
据此本可不出 A/B。**后来仍补做了端到端 A/B**，唯一理由是 `boundaries` 里保留的残余边界——
「kernel/wait 归因**测不到**同步等待的可回收性」——只能用端到端测量销掉。
按纪律**显式说明这次扩展**（不静默改判据）。

**端到端 A/B 实测**（`/root/ops/ab62_20260922_141427`，9/9 有效，卡时 ≈0.34）——
★ **口径统一为 `savings_pct = (基线 − 候选) / 基线 × 100`，正号 = 候选更快**（v2 角色制）：

| 候选 | 做了什么 | `savings_pct` | 95% 区间 | `62` v2 判定（退出码） |
|---|---|---|---|---|
| **C1** | 跳过 `clip_grad_norm`（范数计算 + 归约） | **+1.7645%** | **[−4.4405, +7.9695]** | `PERFORMANCE_NOT_MET`（4） |
| **C2** | 跳过 loss 的 DP `all_reduce` | **+0.0194%** | **[−1.8965, +1.9353]** | `PERFORMANCE_NOT_MET`（4） |

★ **本组数字与外部复核的独立复算逐位一致**（复核值：C1 1.76%、[−4.44, 7.97]；
C2 0.019%、[−1.90, 1.94]）。

**注入自证（正对照，纪律 #3）**：C1 三轮 `grad_norm` 打印全为 **0.0**，而 N/C2 为 **~34.17**
⇒ 注入**确实改变了执行路径**，排除了「设了环境变量但代码没生效」这种假阴性。

★★ **结论的边界（更正后，务必照此表述）**：
C1 的 95% 区间上界 **7.97% > 5%** ⇒ 本实验**既不能确认达标、也不能把它证伪**。
因此 **不得**写「数学上已证明达不到 5%」。停止投入这条线的理由是三条：
① **证据不足**（区间跨零、n=3）；② **点估计小**（1.76%）；③ **代价大于收益**（见下：破坏两条观测链）。
**两条独立证据的关系（更正表述）**：C1 端到端点估计 **+1.76%** ↔ kernel 归因的 **Duration 占比 0.87%**
（≈稳态步的 1.31%）—— **同量级**。端到端测量**已经包含**了「移除同步点所省下的等待」，
结果仍只有 ~1.8% ⇒ **「去掉同步点能省更多」这条替代解释被排除，残余边界（同步等待可回收性）就此销掉**。
另：C2 点估计 +0.02% ⇒ 每步 1 个标量 `all_reduce` 在这条配置上**没有可测成本**。

⚠️ **但请注意「0.87%」的正确含义**：它是**单次 profile 里两个算子的 kernel 时间占比**，
**不是**端到端省时的置信上界，**不得**用来宣称「收益不可能达到 5%」（C1 区间上界 7.97% 就超过 5%）。

**归因数字**（`kernel_details.csv`，35750 行 / 5 步，总 kernel 时间 3161607 us）。
★ 聚合结果已落盘为**证据件** `远端证据_20260922/profile/prof62_20260922_140144__kernel_attribution.json`
（含 provenance：由 `_rcmd_prof62_analyze.sh` 在远端只读聚合；同目录另有本次 profile 的 `result.json` 原件），
**数字可逐项追到该产物**：

| 目标 | kernel | 调用数 | Duration 占比 | Wait 占比 |
|---|---|---|---|---|
| C1 `clip_grad_norm` | `LpNormV2` | 1600（320/步） | **0.45%** | 5.55% |
| C2 loss all_reduce | hccl `allReduce` | 40（8/步） | **0.42%** | 0.24% |
| **合计** | | | **0.87%**（≈稳态步的 1.31%） | — |

**为什么「wait 5.55%」不能算成可回收收益**：LpNormV2 的 `wait/dur = 32.4×` 看着吓人，但这是**小算子排在大算子后面的排队现象**——同类小算子 Cast 7.6×、Transpose 5.7×、Add 3.0×，而大算子 MatMulV3 只有 0.64×。wait 在桶里落在 Free（高度重叠、不可相加），**移除一个正在排队的算子只会把 wait 让给别的算子**，不会等量变成收益。

**真正让这两个候选不值得做的，是第 ④ 步的另一半——观测代价**：
- 跳过 grad-norm 会**打断观测指纹**（`sk04_judge/scripts/fingerprint_observed.py` 要求 `grad norm:` 并把它写进指纹），改成哨兵值则那一维**空过**（坑 33 同族）；
- `scripts/59_config_ab.py` 的 `PAT` **要求** `grad norm:` 同现，否则**计时行一行都解析不出来** ⇒ 连性能测量本身都失效；
- 跳过 loss all_reduce 会把打印的 loss 从「DP 平均」换成「本地 rank 值」，**改变整条 loss 数值链的语义**（C1/C3 分岔定位、逐步 batch 指纹、`70_judge` 逐点判据都建立在它之上）。

⇒ **用 ≤0.87% 的算子时间去换掉两条观测链，是净亏。** 这正是本流程把「正确性/资源检查」放在「选档」之前的理由：**一个优化候选的代价不只是时间。**

**副产品（下一步该往哪走）**：同一份 profile 指出真正的大头是

## 6. 已知边界（**必须**随结论一起说）

1. **主结论是同机同 mock 口径**：`official_comparable=false` ⇒ 只能说"同机同批次的相对差
   19.606%"，**不得**声称"优于官方基线"。要让口径升级到 `official_comparable=true`，
   唯一的路是改用官方全量同源数据（COCO，19.3 GB）重跑 A/B（属**用户决策项**）。
2. **底噪目前是"协议里的文字记录"，不是"归档的机器产物"**：
   本轮复算用的 `null_summary.json` 是**依据协议记录重建**的复算输入，
   原始 `null_summary.json` 未随包归档 ⇒ **下次实验必须把 `null_summary.json` 一并归档**，
   否则 `62` 的 C1 关永远只能靠人工抄数（这是本流程目前唯一的"靠人"接缝）。
3. **`62` 只把关上面 C1–C4**，它**不**替精度背书（那是 `70_judge.py` 的事），
   也**不**判断候选是否值得做（那是人的取舍）。
4. **95% 区间跨 0 时只告警、不改判**：本闸门不去发明第五条判据；引用时**必须**同时给出区间。

## 7. 接线（单一来源）

| 环节 | 工具 | 说明 |
|---|---|---|
| 量底噪 | `59_config_ab.py --null-test N` | 产出 `null_summary.json`（`p59null.v1`） |
| 跑 A/B | `59_config_ab.py --key/--a/--b`、`63_two_config_ab.py` | 产出 `summary.json`（`p59ab.v2` / `t63_two_config_ab.v1`） |

| ★ **版本对照** | **`工具_重建/hash_consistency.py`** | **跑任何远端实验之前先跑一次**：分别记录远端（运行侧）与本地（判据侧）代码的 sha256，并把"远端那份被当判据用"判为 `JUDGE_SKEW` |
| 正确性 | `70_judge.py` + `59 --null-test` 的数值正对照 | 逐点判据的前置条件 |
| 资源 | `56_profile_run.py` | 桶/算子/栈/显存 |
| 自检（0-GPU） | `62_reportability.py --selftest` | 30 例（含 2 例**真的起子进程**的端到端断言）；同时断言**原因码 + 最终 JSON + 退出码** |
| 自检（0-GPU） | `工具_重建/hash_consistency.py --selftest` | 6 例；**判据偏斜必须被识别** |

★ **版本偏斜不是"靠人记"的事**（坑 216）：端到端 A/B 的编排脚本原本在**远端**复用 `59` 的判据，
而远端那份是旧版（无 `win_ms_of`）⇒ **判据语义会随副本版本漂移**。
现在的分工是硬规矩：**远端只允许「跑」，不允许「判」**；
`hash_consistency.py` 把这件事变成可自动发现的 `JUDGE_SKEW`，而不是操作者的记忆负担。
（G33 只跑它的**自检**；联网那次运行是流程步骤，不当闸门——会话断了会造成假失败。）

**闸门**：`prepush_check.py` 的 **G32** 跑 `62 --selftest`。
自检覆盖**判据层 + 逐对口径换算 + 解析层**（含"无 schema 标签"这条真实路径），
不只覆盖"能不能打印"（坑 192 的教训：只断言过程打印会漏掉结论错）。
